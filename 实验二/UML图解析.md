# 实验二 UML 图解析

项目为**校园二手交易系统**。设计以实验一的需求规格说明书 v2 和本地 Git 标签 `lab1-final`（提交 `81b7509`）为基线。商品发布须经审核，买家预约后与卖家线下交付，系统记录交付约定和完成结果。

五张图覆盖四种 UML 图。类图和组件图描述静态结构，两张状态图描述商品和预约各自的状态变化，时序图描述多个请求之间的交互。

## 1. 类图

[打开 PNG](UML/UML类图.png) · [PlantUML 源文件](UML/UML类图.puml)

- **账号与角色。** 从「账号」到「预约」的两条线分别对应买家和卖家。每笔预约有一名买家和一名卖家，每个账号可以在多笔预约中承担不同角色。账号上的管理员标记用于管理操作的授权。用户名以归一化值校验唯一性，密码保存为哈希。
- **商品与预约。** 一个商品可以关联零条或多条历史预约，商品的 `activeReservationID` 单独指向当前有效预约。商品被预约、释放或完成时，用这个关联确认本次操作针对的是哪一笔预约。旧预约的取消或过期任务遇到后继预约时，关联检查会阻止它释放新占用。
- **内容与约定。** 商品支持未填全的草稿，提交审核时才检查商品必填字段和图片限制。审核提交保存提交编号和内容快照，管理员审核的是当前提交。预约在创建时保存约定价格、时间和地点，成交统计读取预约时的价格与首次完成时间。
- **操作结果和日志。** 操作结果用于按提交标记恢复已处理请求。审计日志记录操作者、对象、动作、时间、前后状态、结果和适用原因，也用于记录管理员查看交付信息的动作。系统到期任务可以使用系统身份写入记录。

主要对应 REQ-001～008、REQ-012～013、REQ-019、REQ-021、REQ-023～026、REQ-029。

## 2. 组件图

[打开 PNG](UML/UML组件图.png) · [PlantUML 源文件](UML/UML组件图.puml)

箭头由调用方指向它依赖的模块。交易端和管理端经 Web API 进入同一个应用，业务模块按操作人、目标对象和当前状态授权。访客可以读取公开商品，具体交付约定只向本预约双方和获授权的管理员开放。

| 模块 | 职责与交互 |
|---|---|
| 账号与权限 | 注册、会话、管理员授撤权与对象授权。撤权时检查是否至少还保留一名有效管理员。 |
| 商品管理与浏览 | 管理草稿、图片、公开列表、商品版本和占用。卖家管理自己的商品，公开查询只返回已发布且可预约的商品。 |
| 审核与违规处置 | 对当前提交审批或驳回，处理违规商品。封禁时调用预约模块，以平台原因结束当前有效预约，并通知双方。 |
| 预约与交付 | 校验预约与交付条件，驱动商品占用和预约状态的联动。到期任务复用预约模块的过期处理。 |
| 操作记录 | 记录关键变更和管理员敏感访问，并按当前对象权限查询。普通用户的日志查询限制在其参与的交易内。 |
| 交易统计 | 读取当前商品状态数量及指定时间段的已完成预约。当前状态数量独立于成交日期筛选，成交按北京时间的左闭右开区间和首次完成时间计入。 |

应用内共用关系数据库和事务接口，预约服务可以在同一次提交中保存商品占用、预约、操作结果及成功日志。商品图片作为文件保存，数据库记录它与商品的关联及访问所需的元数据。

主要对应 REQ-001～027、REQ-029～030，其中 REQ-024 约束跨模块写入的事务边界。

## 3. 商品状态图

[打开 PNG](UML/UML状态图_商品.png) · [PlantUML 源文件](UML/UML状态图_商品.puml)

从初始圆点出发，卖家先创建草稿。箭头的方括号给出执行条件，斜杠后的文字给出执行后的动作。

1. **审核与上架。** 草稿、已驳回、已下架的商品资料完整时可提交审核。待审核时可以撤回到草稿。管理员只处理当前提交，驳回须填写原因。首次通过或内容改变后通过时更新发布时间，未改内容的下架重审沿用原发布时间。
2. **预约与成交。** 预约成功时商品立刻从已发布进入已预约。普通取消、拒绝、过期只释放该笔当前占用，商品恢复已发布并沿用原发布时间。买家在卖家确认后确认收到实物，商品与预约同时进入已售出和已完成。
3. **违规处置。** 图中的外框标出管理员可封禁的五种商品状态。存在有效预约时，封禁和预约取消在同一事务中保存。已售出的商品可以追加违规标记，图中的自环表示该操作后的状态仍是已售出。

主要对应 REQ-005～012、REQ-017～020、REQ-022、REQ-024。

## 4. 预约状态图

[打开 PNG](UML/UML状态图_预约.png) · [PlantUML 源文件](UML/UML状态图_预约.puml)

「待卖家确认」和「卖家已确认」都占用商品。截止时刻取创建后 24 小时与约定交付时间中的较早者。服务器时间等于或超过截止时刻时，待确认预约进入过期处理。后台正常运行时在截止后 60 秒内处理，确认和新预约入口遇到到期记录时也先处理过期。

| 当前状态 | 允许的主要动作 |
|---|---|
| 待卖家确认 | 本单卖家可以在截止前接受，也可以有理由地拒绝。买家可以取消。到期时核对仍关联的是本预约，然后结束占用。 |
| 卖家已确认 | 双方均可填写原因取消，买家可确认已收到实物并完成预约。 |
| 两种有效状态 | 管理员封禁商品时，预约按平台原因取消，商品进入已封禁，双方收到处置结果。 |

预约完成、取消、拒绝和过期后，历史记录仍可按原业务权限查询。过期与随后的确认或新建是独立操作，已经提交的过期和释放结果会保留。

主要对应 REQ-004、REQ-010、REQ-012～020、REQ-022～025。

## 5. 并发预约时序图

[上页 PNG](UML/UML时序图_并发预约.png) · [续页 PNG](UML/UML时序图_并发预约_001.png) · [PlantUML 源文件](UML/UML时序图_并发预约.puml)

从上往下读。图中两名买家都从同一件已发布商品发起首次预约，先取得商品行锁的请求以 A 为例。

1. Web API 分别确认两名买家的身份与操作权限。预约服务先按用户、动作和提交标记查操作结果，再对新请求检查当前商品版本和占用。相同标记的请求还要比对目标和业务参数。
2. A 持有商品行锁。它在同一事务内写入待卖家确认的预约、商品占用、成功日志和操作结果，提交后才能报告成功。提交前写入失败时回滚这次操作的写入。竞争请求取得锁后按实际提交的状态重新判断。
3. B 等到 A 提交后才取得锁，读到商品已预约，回滚本次业务事务并独立记录失败原因，随后提示「商品已被预约，请刷新页面」。服务端通过商品行锁和重新校验控制商品占用。数据库对处于有效状态的预约按商品编号建立条件唯一约束。
4. 如果 A 的成功响应在返回途中丢失，可以按原标记和原内容重试。系统重新认证并检查结果关联预约的读取权限，返回原预约号与当前状态。执行新提交时先通过用户、动作、标记的唯一约束取得执行权。并发重试可以等待已处理结果，复用标记但内容不同会返回冲突。

主要对应 REQ-004、REQ-012、REQ-019、REQ-021～025、REQ-028、REQ-030、REQ-032。
